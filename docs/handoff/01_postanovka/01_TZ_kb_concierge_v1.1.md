# ТЗ: агент-дирижёр экосистемы reHome — «Консьерж» (`kb-concierge`)
### Версия 1.1 · 2026-06-11 · для разработки Клодом (Claude Code), двухагентная схема
### Компаньон к «ТЗ: модуль обработки партнёрских заявок `kb-partners`»

> **Назначение.** Техническое задание на сервис-оркестратор — **единый ИИ-вход для всех обращений пользователя за помощью**: информационные запросы, вопросы-ответы, заявки на партнёрские услуги, нестандартные ситуации и проблемы. Агент распознаёт намерение, отвечает сам там, где может, маршрутизирует обращение в нужную способность (KB / kb-support / kb-partners), действует автономно **в рамках политики** и передаёт человеку всё, что выходит за её пределы.
>
> **Принцип проектирования (ключевой).** «Единая экосистема под управлением ИИ» реализуется как **оркестрация поверх слабо связанных детерминированных модулей**, а не как растворение их в общем «ИИ-ядре». LLM — это рассуждающий дирижёр, но он **никогда не находится в критическом пути детерминированных операций** (деньги/escrow, `access_level`, машины состояний, «4 глаза»). Эти операции остаются за авторитетными модулями; агент лишь вызывает их как инструменты.
>
> ТЗ построено **contract-first** и снабжено проверяемыми acceptance-критериями — под двухагентную схему разработки (агент-исполнитель + агент-ревьюер). Пометки `[ДЕФОЛТ — подтвердить]` фиксируют развилки до решения Архитектора (сводка — §13).
>
> **Изменения v1.1.** Добавлено: делегирование прав пользователя (on-behalf-of / OAuth2 token-exchange); подтверждение пользователем платных/необратимых действий перед выполнением; явная деградация при недоступности LLM; сквозной `correlation_id` для трассировки; rate-limiting публичного входа; ориентиры SLO.

## 1. Контекст и цель

### 1.1 Зачем
Сейчас у пользователя несколько разрозненных точек входа (AI-чат базы знаний, форма поддержки, будущая партнёрская форма). `kb-concierge` делает **один вход**, за которым стоит вся экосистема: пользователь пишет «как продлить договор», «нужен клининг в субботу» или «сосед затопил, что делать» — и получает либо прямой ответ, либо запущенное действие, либо корректную передачу оператору.

### 1.2 Что агент покрывает
| Класс обращения | Куда ведёт | Способность |
|---|---|---|
| **Информация / вопрос-ответ** | KB (kb-search RAG) | прямой ответ с цитатами |
| **Заявка на партнёрскую услугу** | kb-partners | `ServiceRequest` (приём→классификация→диспетч) |
| **Проблема / жалоба / претензия** | kb-support | тикет / claims-контур |
| **Нестандартная ситуация** | сбор контекста + эскалация | по умолчанию — человек |

### 1.3 Чем агент НЕ является
- Не владеет данными и не дублирует домены модулей.
- Не считает деньги, не проводит выплаты, не вычисляет права доступа.
- Не «решает» нестандартные/претензионные ситуации самостоятельно — он их корректно квалифицирует и передаёт.
- Не реализует рантайм модулей внутри себя; вызывает их по API.

### 1.4 Рабочее имя
Рабочее имя — **«Консьерж»**; кодовое имя сервиса — `kb-concierge`. **Зафиксировано.**

## 2. Границы (scope)

**Входит:**
- Единый conversational-вход (turn-based диалог) поверх каналов (AI-чат kb-search в первую очередь; веб/моб-приложение).
- Распознавание намерения и маршрутизация (intent router).
- Слой инструментов (typed tools) над KB / kb-support / kb-partners / rehome.one (read-only контекст).
- Агентный цикл рассуждения с ограничениями (bounded loop).
- **Политика автономности** и **guardrails** (§7 — ядро ТЗ).
- Бесшовный **human-handoff** в kb-support с передачей контекста и возвратом ответа оператора в диалог.
- Сборка контекста и сессионная память; ПДн-маскировка перед LLM; right-to-forget.
- Аудит решений/вызовов агента; наблюдаемость и eval-гейты (через kb-eval).

**НЕ входит (делают модули):**
- Хранение знаний/тикетов/заявок, расчёт денег, проводка платежей, вычисление `scope`/`access_level`, машины состояний — за KB / kb-support / kb-partners / платёжным контуром.
- Сам RAG-движок — в kb-search; агент его вызывает.

Frontend поверхность переиспользует AI-чат kb-search `[ДЕФОЛТ — подтвердить, §13.3]`.

## 4. Доменная модель

Все сущности несут `access_level`; фильтрация на хранилище; недоступный ресурс → 404.

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| **AgentSession** | диалоговая сессия | id, user_id?, channel, status, started_at, ttl, summary |
| **AgentTurn** | реплика диалога | session_id, role (user/agent/tool/system), content, content_masked, intent?, confidence?, ts |
| **AgentAction** | решение/действие агента | turn_id, type (answer/tool_call/handoff/clarify), tool_name?, args_redacted, result_ref, autonomous (bool), ts |
| **ToolCall** | вызов инструмента | action_id, tool, request_idempotency_key, status, latency, provider_status, ts |
| **AutonomyPolicy** | правила автономности | intent, allowed_actions[], thresholds, mandatory_handoff[], version, active |
| **HandoffRecord** | передача человеку | session_id, reason, target (kb-support ticket_id), context_snapshot_ref, ts |
| **AuditLog** | неизменяемый аудит | actor_id (agent SP / user), action, from/to, ts |

Сессионная память хранит **только необходимое**; ПДн в `*_masked`-полях; soft-delete / right-to-forget.

## 5. Распознавание намерения и маршрутизация (intent router)

- **FR-5.1** Классифицировать обращение в одно из намерений: `INFO_QA`, `PARTNER_SERVICE`, `SUPPORT_ISSUE`, `NON_STANDARD` (+ `SMALL_TALK`/`OUT_OF_SCOPE`).
- **FR-5.2** Гибридно: быстрые детерминированные правила (ключевые слова/канал/контекст) → при неоднозначности LLM-классификация через `LLMProvider`.
- **FR-5.3** Возвращать `intent` + `confidence` + извлечённые слоты (для PARTNER_SERVICE — категория/параметры; для SUPPORT_ISSUE — тип проблемы).
- **FR-5.4** Версионирование промптов/модели; полная трассируемость решения (метод/модель/версия/уверенность) в `AgentTurn`/`AuditLog`.
- **FR-5.5** Многошаговые диалоги: уточняющие вопросы (`clarify`) при недостатке слотов — но в пределах лимита шагов (§6).

## 6. Агентный цикл (reasoning loop)

- **FR-6.1** Цикл: восприятие → план → вызов инструментов → наблюдение → ответ/уточнение/эскалация.
- **FR-6.2** **Ограничения (bounded loop):** максимум шагов/вызовов инструментов на сессию-ход, таймаут, бюджет токенов; при исчерпании — `clarify` или `handoff`, не зацикливание.
- **FR-6.3** Каждый шаг и каждый tool-call — запись в `AgentAction`/`ToolCall`/`AuditLog` с `actor_id = agent service principal`.
- **FR-6.4** Идемпотентность: повтор одного и того же намерения в рамках хода не порождает дублей действий/заявок (idempotency keys на исходящих).
- **FR-6.5** Детерминированный результат на стороне модуля — авторитетен; агент не «придумывает» статусы/суммы/права, а отражает ответ инструмента.
- **FR-6.6** **Деградация при недоступности LLM:** если `LLMProvider` недоступен или превышен бюджет — агент переходит на детерминированный роутинг по правилам, а при невозможности — на прямой human-handoff; не падает и не выдумывает ответ.

## 7. Политика автономности и guardrails (ядро ТЗ)

### 7.1 Матрица автономности `[ДЕФОЛТ — подтвердить, §13.1]`
| Намерение | Что агент делает сам (автономно) | Обязательный human-handoff |
|---|---|---|
| **INFO_QA** | Отвечает из KB (RAG) с цитатами источников | Низкая уверенность / нет источника / юридически или финансово чувствительный вопрос |
| **PARTNER_SERVICE** | Создаёт `ServiceRequest`; при `confidence ≥ порог` — подбор + диспетчеризация партнёру **после подтверждения пользователем** (§7.4) | `confidence < порог`, неоднозначные параметры, `FAILED_DISPATCH`, спор |
| **SUPPORT_ISSUE** | Создаёт тикет, классифицирует, наполняет контекст; даёт типовой ответ из шаблона/БЗ | Любая претензия (компенсация/гарантия/страхование), деньги, спор, эмоционально острая ситуация |
| **NON_STANDARD** | Собирает контекст, формулирует резюме для оператора | По умолчанию — **эскалация** (агент не решает нестандартное сам) |
| **Деньги / доступ / выплаты** | **Никогда** | **Всегда** детерминированный контур + «4 глаза» |

### 7.2 Жёсткие guardrails `[ИНВАРИАНТ]`
- **G1.** Агент **не инициирует** расчёт/выплату/escrow сверх вызова контура; «4 глаза» по выплатам сохраняются на стороне модулей.
- **G2.** `scope`/`access_level` — только из проверенного JWT на бэкенде; агент не выдаёт себе прав и не передаёт ресурсы вне области пользователя.
- **G3.** ПДн **маскируются до любого LLM-вызова** и в логах; наружу — `status + title`, без ПДн.
- **G4.** **Защита от prompt-injection и эксфильтрации:** пользовательский ввод и контент из инструментов — недоверенные; агент не исполняет инструкции из них, не раскрывает системные промпты/секреты, не отправляет данные за пределы экосистемы.
- **G5.** Любое действие, эквивалентное необратимому (отмена заказа, закрытие претензии, изменение договора), — **только через инструмент модуля** с его правами/проверками, и не автономно вне матрицы §7.1.
- **G6.** При сомнении — **деградация в сторону безопасности**: уточнить или передать человеку, не действовать.
- **G7.** **Делегирование прав пользователя (on-behalf-of).** Вызовы модулей от имени пользователя несут его делегированную авторизацию (OAuth2 token-exchange / `actor`-claim); модуль применяет `scope`/`access_level` к **пользователю**, а не к сервис-принципалу агента. Агент не может действовать шире прав пользователя; сервис-принципал агента — только для инфраструктурных вызовов.

### 7.3 Human-handoff
- **FR-7.1** Передача в kb-support: создаётся/обновляется тикет с **снимком контекста** диалога (ПДн-маскированным по правилам канала) и причиной эскалации.
- **FR-7.2** Возврат ответа оператора пользователю в тот же диалог (переиспользовать паттерн `operator-reply` kb-support↔kb-search).
- **FR-7.3** Внутренние заметки оператора **никогда** не попадают в диалог с пользователем (инвариант «внутреннее ≠ внешнее»).

### 7.4 Подтверждение платных и необратимых действий
- **FR-7.4** Перед любым действием с **финансовыми последствиями или необратимостью** (заказ платной услуги, отмена заказа, открытие спора) агент **запрашивает явное подтверждение пользователя в диалоге** (что именно, у кого, ориентир стоимости/комиссии) и выполняет действие только после согласия. Без подтверждения действие не инициируется.

## 8. Слой инструментов (tools)

Каждый инструмент — обёртка над API модуля: строгая схема вход/выход, m2m-auth (сервис-принципал агента), идемпотентность, resilient-клиент (timeout→circuit-breaker→retry→метрики).

| Tool | Модуль | Назначение |
|---|---|---|
| `kb.search` / `kb.answer` | kb-search | RAG-поиск и ответ с цитатами |
| `support.create_ticket` / `support.add_message` / `support.get_status` | kb-support | завести/вести обращение |
| `partners.create_request` / `partners.classify` / `partners.dispatch` / `partners.get_status` | kb-partners | партнёрская заявка и её продвижение |
| `platform.get_context` | rehome.one (через адаптер) | контекст User/Premises/Booking — **read-only**, без денег |
| `handoff.to_operator` | kb-support | эскалация человеку |

> Инструменты — это те же agent-ready эндпоинты модулей (kb-partners §11, kb-support, kb-search). Новый инструмент = регистрация в реестре tools + схема, без изменения ядра агента.

## 9. Интеграции

| Контрагент | Что нужно | Механизм |
|---|---|---|
| **Keycloak** | auth пользователя (браузер) + **сервис-принципал агента** (m2m) + **делегирование прав пользователя** | OIDC + Client Credentials + **OAuth2 token-exchange** (on-behalf-of), RS256/JWKS, `verify_aud` |

| **Подписчики** | события агента (handoff, action) | исходящие webhooks (HMAC) |

## 10. API-контракт (OpenAPI-first)

Префикс `/api/v1/concierge`. Сначала `docs/openapi.yaml`, затем контрактные тесты.

- `POST /sessions` — создать сессию (анон/авторизованная).
- `POST /sessions/{id}/messages` — реплика пользователя (SSE-стрим ответа агента).
- `GET /sessions/{id}` — история (scope-фильтр, masking).
- `POST /sessions/{id}/handoff` — принудительная эскалация человеку.
- `DELETE /sessions/{id}` — right-to-forget.
- `GET /policies` / `PATCH /policies/{id}` — управление политикой автономности (staff).
- `POST /inbound/operator-reply` — SERVICE-only: возврат ответа оператора в диалог.
- Исходящие webhooks: `agent.intent_classified / action_taken / handoff_created / answered / clarify_requested`.
- Служебные: `GET /healthz` · `GET /readyz` · `GET /metrics` (Prometheus; рассмотреть VictoriaMetrics при росте ретенции).

**Конвенции:** идемпотентные POST принимают заголовок `Idempotency-Key`; сквозной `correlation_id` в заголовке пробрасывается в вызовы инструментов. Ошибки наружу — RFC 7807 (`type/title/status`), без ПДн; недоступный ресурс — 404.

## 11. Нефункциональные требования и инварианты

`[ОБЯЗАТЕЛЬНО]`:
1. **Отдельный сервис, слабая связанность:** своя БД/репо/деплой; интеграция только по API; enforce в CI (`check-arch-constraint.sh`). Сбой агента не роняет модули; сбой модуля деградирует агента (он отвечает «обработаю позже»/эскалирует), а не падает.
2. **«Разрабатываем сами»:** новые внешние зависимости — только через ADR.
3. **Двухконтурность:** `access_level`, фильтр на хранилище, 404-не-403.
4. **scope — только на бэкенде** из проверенного JWT.
5. **ФЗ-152:** хостинг и обработка ПДн в РФ; маскировка перед LLM и в логах; soft-delete / right-to-forget.
6. **Аудит:** все решения/вызовы агента — неизменяемые записи с `actor_id` (сервис-принципал агента).
7. **Внутреннее ≠ внешнее.**
8. **Идемпотентность** ходов и исходящих; **outbox** для событий.
9. **Resilience:** все клиенты — timeout→circuit-breaker→retry→метрики, cache-aside; критичные операции не кешируются.
10. **AI-специфичные:** ПДн-маскировка до LLM; объяснимость (трасса решения); LLM **вне** критического пути детерминированных операций; bounded loop; eval-гейты качества.
11. **Делегирование прав:** действия от имени пользователя — через token-exchange (on-behalf-of); агент не превышает прав пользователя.
12. **Rate limiting / анти-абьюз:** лимиты на публичный turn-эндпоинт и защита от злоупотреблений.
13. **Трассировка:** сквозной `correlation_id` пробрасывается во все вызовы инструментов (end-to-end через модули).
14. **SLO (ориентир, уточнить):** время до первого токена ответа p95 < 1.5 с; маршрутизация p95 < 2 с; не более N шагов/вызовов на ход.

## 12. Acceptance-критерии (проверяемые)

Служат гейтами для агента-ревьюера; часть проверяется через kb-eval.

- **Маршрутизация.** На golden-наборе kb-eval точность классификации намерения ≥ целевого порога `[ДЕФОЛТ — подтвердить]`; ошибочные/неуверенные кейсы уходят в `clarify`/`handoff`, а не в неверное автономное действие.
- **Автономность.** Агент выполняет автономно **только** действия из матрицы §7.1; любые претензии/деньги/нестандартное → handoff; нарушений в тест-наборе ноль.
- **Деньги/доступ.** В тестах нет ни одного автономного денежного действия; «4 глаза» соблюдены на стороне модулей; агент не выдаёт ресурсы вне scope пользователя (запрос чужого → 404).
- **ПДн.** Ни один LLM-вызов и ни одна запись лога не содержат немаскированных ПДн (паттерн-тесты).
- **Injection.** Набор атак prompt-injection/эксфильтрации не приводит к раскрытию системного промпта/секретов, к выходу за scope или к запрещённому действию.
- **Bounded loop.** Нет бесконечных циклов; при исчерпании лимита — `clarify`/`handoff`; таймаут соблюдается.
- **Идемпотентность.** Повтор хода не создаёт дублей тикетов/заявок.
- **Handoff.** Эскалация создаёт тикет со снимком контекста; ответ оператора возвращается в диалог; внутренние заметки не утекают.
- **Аудит.** 100 % действий агента атрибутированы и трассируемы.
- **Деградация.** При недоступности модуля агент корректно деградирует (отвечает/эскалирует), не падает.
- **Делегирование.** Действия от имени пользователя несут on-behalf-of-авторизацию; в тестах агент не получает доступ сверх прав пользователя (чужой ресурс → 404).
- **Подтверждение.** Платные/необратимые действия не выполняются без явного согласия пользователя в диалоге.
- **LLM-деградация.** При недоступности LLM агент переходит на правила/handoff, не падает.
- **Rate-limit.** Превышение лимита публичного входа корректно отбивается.
- **Сквозное.** `check-arch-constraint.sh` зелёный; OpenAPI-валидация зелёная; ошибки наружу без ПДн; `correlation_id` присутствует во всех связанных вызовах.

## 13. Открытые вопросы к Архитектору

1. **Матрица автономности (§7.1)** — финальные пороги уверенности и перечень автономных действий по каждому намерению; что из SUPPORT_ISSUE агент вправе закрывать сам.
2. **Провайдер LLM по умолчанию** и политика переключения; требования к латентности/стоимости хода.
3. **Диалоговая поверхность** — расширять AI-чат kb-search или вести собственный слой сессий в `kb-concierge` (§3).
4. **Память/ретенция** сессий: TTL анонимных/авторизованных, объём контекста, политика right-to-forget.
5. **Eval-набор**: владелец golden-данных по маршрутизации/ответам и целевые пороги качества (§12).
6. **Поверхности входа в MVP**: только AI-чат или сразу веб/моб.
7. Механизм делегирования прав пользователя (OAuth2 token-exchange) и его поддержка в Keycloak-realm — §7.2/G7, §9.
8. Политика подтверждения платных/необратимых действий: какие действия требуют явного согласия и форма подтверждения — §7.4.

## 14. Организация разработки — двухагентная схема

Та же схема, что для KB / kb-support / kb-partners `[сверить точное разделение с вашим процессом]`:
- **Агент-исполнитель** реализует эпик строго под OpenAPI (§10), доменную модель (§4) и матрицу автономности (§7).
- **Агент-ревьюер** проверяет против acceptance-критериев (§12), инвариантов (§11) и guardrails (§7.2); особое внимание — безопасности (деньги/доступ/ПДн/injection). Не пропускает эпик, пока гейты не зелёные.
- Контур повторяемости: OpenAPI-first → контрактные тесты → arch-constraint в CI → eval-гейты kb-eval → программная сборка артефактов.

**Порядок эпиков:** каркас+auth+OpenAPI → Conversation/Session → Intent Router → Tool Layer (read-only сначала: `kb.search`, `platform.get_context`) → Policy Engine + Guardrails → Reasoning Loop → Human-handoff → write-инструменты (`support.*`, `partners.*`) под политикой → eval-гейты и наблюдаемость.

**Что дать обоим агентам на вход:** этот ТЗ + ТЗ `kb-partners` + OpenAPI трёх модулей + ADR (0001/0003/0004/0005/0006/0007/0008/0013–0017) + `CLAUDE.md` kb-support + `check-arch-constraint.sh` + подтверждённые ответы §13 + acceptance-критерии (§12) в машиночитаемом виде.

## 15. Связь с ТЗ `kb-partners`

`kb-concierge` и `kb-partners` спроектированы как пара: kb-partners уже сделан **agent-ready** (идемпотентные эндпоинты-инструменты + события + политика автономности на своей стороне), поэтому `kb-concierge` подключает его без доработок ядра. Аналогично он использует уже существующие способности KB (kb-search) и kb-support. Это и есть «единая экосистема под управлением ИИ» в безопасной форме — **оркестрация над модулями**, сохраняющая fault-isolation и детерминизм денег/доступа.
