# ADR-0001 — Архитектурная константа kb-concierge

- Статус: Принято (2026-06-11)
- Контекст: ТЗ «Консьерж» v1.1 §1.3, §2, §3, §11

## Контекст

`kb-concierge` — ИИ-агент-оркестратор: единый вход, распознавание намерения,
маршрутизация и автономные действия в рамках политики. Риск антипаттерна —
«растворить» детерминированные модули в общем «ИИ-ядре».

## Решение

**Оркестрация поверх слабо связанных детерминированных модулей** (а не общий ИИ-монолит):

1. **Отдельный сервис:** своя БД (сессии/реплики/аудит/политики/версии промптов),
   свой репозиторий, свой деплой. Связь с соседями (KB/kb-search, kb-support,
   kb-partners, rehome.one, kb-eval, Keycloak) — **только по сети, по API**, как
   typed-tools поверх resilient HTTP-клиентов. Никаких общих таблиц / общего кода / монорепо.

2. **LLM вне критического пути детерминированных операций.** Деньги/escrow,
   `access_level`, машины состояний, «4 глаза» — за авторитетными модулями. Агент
   их вызывает, не дублирует и не «придумывает» результат.

3. **Fault-isolation:** сбой агента не роняет модули; сбой/недоступность модуля
   **деградирует** агента (отвечает «обработаю позже» / эскалирует человеку), а не валит его.

4. **Enforce:** `scripts/check-arch-constraint.sh` (CI job `arch-constraint`) запрещает
   импорт кода соседей и прямой SQL к чужим таблицам (users/tickets/service_requests/
   service_orders/kb_*/...). Легитимные исключения — inline `# arch-allow: <обоснование ≥10 chars>`.

## Последствия

- Новый инструмент = регистрация в реестре tools + схема, без изменения ядра агента.
- Детерминизм денег/доступа и отказоустойчивость сохраняются при «ИИ-управлении».
- Безопасность (ПДн/scope/injection/«4 глаза») — инвариантно на стороне модулей и guardrails (§7.2 ТЗ).
