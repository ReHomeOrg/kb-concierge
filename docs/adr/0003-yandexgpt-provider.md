# ADR-0003 — Боевой LLM-провайдер intent-роутера: YandexGPT

- Статус: **Предложено** (2026-06-12) — ожидает approve Архитектора
- Контекст: ТЗ «Консьерж» v1.1 §5 (Intent Router), FR-5.2, FR-6.6; CLAUDE.md правило 6
- Связанные: ADR-0001 (арх-константа), kb-partners ADR-0003, rehome-kb-platform ADR-0013

## Контекст

Intent-роутер (§5) распознаёт намерение обращения по схеме **rules → LLM**: при
однозначном rules-совпадении LLM не вызывается; при неоднозначности/отсутствии
совпадений зовётся `LLMProvider`. До настоящего ADR в Консьерже реализован только
`NullLLMProvider` (LLM-путь инертен → работает детерминированный rules-путь). Контракт
`LLMProvider.classify(masked_text) -> LLMIntent | None` был зафиксирован заранее, чтобы
подключение боевого провайдера не меняло сервисный слой.

CLAUDE.md правило 6 («разрабатываем сами, не подключать внешние сервисы без ADR»)
требует зафиксировать решение о подключении внешнего LLM до его реализации.

Открытые вопросы перед стартом:

- Какой провайдер — основной боевой для экосистемы reHome?
- Вендорский SDK или собственный HTTP-адаптер?
- Как соблюсти ФЗ-152 (ПДн на территории РФ) и guardrails G3/G4 (ПДн/anti-injection)?
- Как провайдер деградирует при недоступности (FR-6.6)?

## Решение

### 1. Провайдер — YandexGPT (Yandex Foundation Models)

Основной боевой LLM-провайдер экосистемы — **YandexGPT**. Причины: размещение в РФ
(ФЗ-152), уже боевизирован у соседей (`kb-partners`, `rehome-kb-platform/kb-search`) —
единый провайдер для всей экосистемы (см. ТЗ «Единая экосистема» §7.1). Имена
`gigachat`/`vllm`/`mock` зарезервированы под будущие ADR и пока резолвятся в `Null`.

### 2. Собственный HTTP-адаптер, без вендорского SDK

`YandexGptProvider` — свой адаптер поверх `ResilientHttpClient` (`api/clients/`):
Api-Key-авторизация (`Authorization: Api-Key …` + `x-folder-id`), эндпоинт
`POST /foundationModels/v1/completion`, `modelUri = gpt://<folder>/<model>/latest`,
`temperature=0.0`. Никакой новой внешней зависимости (соблюдение правила 6); сеть
проходит через единый resilience-контур (timeout → circuit breaker → retry).

### 3. ФЗ-152 и guardrails

- **G3 (ПДн).** В модель уходит **только маскированный текст** (ПДн вырезаны до LLM);
  текст обращения в логи не пишется.
- **G4 (anti-injection).** Системный промпт фиксирован и содержит только имена классов
  `Intent`; пользовательский текст — недоверенный, инструкции из него не исполняются.
- Креды (`yandexgpt_api_key`) — ссылка на kb-vault, в коде/репозитории отсутствуют.

### 4. Деградация (FR-6.6, fail-safe)

Недоступность / 4xx-5xx / неразбираемый ответ / неизвестное намерение → `classify`
возвращает `None`; `IntentClassifier` уходит на rules-путь (низкоуверенный результат
или `OUT_OF_SCOPE`), Консьерж не падает и не выдумывает намерение. Включение —
строго по конфигурации: `intent_llm_provider=yandexgpt` **и** заполненные
`yandexgpt_api_key`/`yandexgpt_folder_id`; иначе — `NullLLMProvider` (rules-only).

## Последствия

- Включение боевого LLM — конфигурацией (env `KBC_*`), без изменения сервисного слоя.
- Для активации в проде нужны **креды YandexGPT** (kb-vault) и `folder_id` Yandex Cloud —
  это ops-провижининг, вне кода (см. ТЗ «Единая экосистема» §12, Э1/Э6).
- Контракт `LLMProvider` остаётся стабильным — добавление `gigachat`/`vllm` потребует
  лишь нового адаптера и отдельного ADR.
- Тесты — без сети (`httpx.MockTransport`); живой вызов модели валидируется при наличии
  кредов на eval-стенде (kb-eval, decision-golden).

## Альтернативы (отклонены)

- **Вендорский SDK `yandexcloud`/`yandex-gpt`** — лишняя внешняя зависимость, нарушает
  правило 6; HTTP-адаптер проще контролировать и тестировать.
- **GigaChat / vLLM как основной** — отложено; YandexGPT уже боевизирован у соседей,
  единообразие экосистемы важнее на старте.
- **LLM всегда (без rules-fast-path)** — дороже и медленнее; rules→LLM экономит вызовы
  на однозначных обращениях (FR-5.2).
