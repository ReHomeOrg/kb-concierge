## 🔴 Сквозные находки (затрагивают ВСЕХ соседей)

### CC-1 [BLOCKER] Делегирование прав через `X-On-Behalf-Of` не работает нигде
Консьерж шлёт HTTP-заголовок `X-On-Behalf-Of` во все модули (partners/support/search/platform). **Ни один сосед его не читает.** Делегирование прав пользователя (guardrail G7, on-behalf-of) у соседей ожидается через **OAuth2 token-exchange — claim в самом Bearer-токене** (у kb-partners это `kbp_act_sub`), а не через кастомный заголовок.
**Последствие:** агент действует как сервис-принципал без привязки к пользователю → scope-фильтрация (404 на чужой ресурс) работает не так, как рассчитывает Консьерж; G2/G7 не соблюдаются.
**Фикс:** получать делегированный токен через token-exchange и класть в `Authorization: Bearer`; заголовок `X-On-Behalf-Of` убрать. Единая правка в `clients/*/adapter.py` + `clients/auth.py`.

### CC-2 [MINOR] Несогласованный заголовок трассировки
Консьерж шлёт `X-Correlation-Id`; соседи его не читают (kb-support ждёт `X-Request-Id`, partners/search — никак). Сквозная трасса (NFR-13/correlation_id) на стороне соседей не сшивается. На сам вызов не влияет.
**Фикс:** согласовать единое имя заголовка корреляции по экосистеме (рекомендуется `X-Request-Id` как у kb-support) и проставлять его в `ResilientHttpClient`.

| # | Серьёзность | Расхождение | Фикс |

| P-1 | **BLOCKER** | `on_behalf_of` шлётся как `X-On-Behalf-Of` (`adapter.py:36`), сосед читает claim `kbp_act_sub` из JWT (см. CC-1) | token-exchange → Bearer |

**Вывод:** готов к включению после фикса делегирования (CC-1/P-1).

## 3. KB / kb-search — нужны правки + у соседа нет openapi (4 BLOCKER)

**Источник контракта:** `rehome-kb-platform` **не имеет** `docs/openapi.yaml` → выведено из роутов (`backend/src/api/search/router.py`, `search/schemas.py`, `chat/*`).

| # | Серьёзность | Расхождение | Фикс |
|---|---|---|---|
| K-1 | **BLOCKER** | Консьерж шлёт `GET /api/v1/search` (`adapter.py:46`); сосед — `POST` (`@router.post("")`) → 405 | перейти на POST с JSON-телом |
| K-2 | **BLOCKER** | Запрос: `params={"q":...}`; сосед ждёт тело `{"query":...}` (`SearchInput`, `extra="forbid"`) → 422 | тело `{"query":..., "limit":...}` |
| K-3 | **BLOCKER** | Корень ответа: `payload.get("results")` (`adapter.py:64`); реально `data` (`SearchResponse.data`) → цитаты всегда пусты | `payload.get("data")` |
| K-4 | **BLOCKER** | `payload.get("answer")` — поля нет в `/search`; RAG-синтез только в chat-роуте `POST /api/v1/chat/sessions/{id}/messages` (SSE/JSON) | **РЕШЕНО Архитектором 2026-06-12 (вариант 2):** `kb.search` остаётся retrieval-цитатами (`answer` убрать), RAG-ответы — **отдельный инструмент поверх chat-роута**. Завести `clients/search` (или новый `clients/chat`) метод поверх `POST /api/v1/chat/sessions/{id}/messages` |
| K-5..9 | MINOR | `snippet` бывает `null`; `score`/`type` игнорируются; default `limit` разный; `X-On-Behalf-Of` (CC-1); correlation | защитить `snippet`, по желанию прокинуть `score` |

**Вывод:** **не готов**. Текущий адаптер на живом kb-search стабильно получал бы 405/422 и **тихо деградировал** в `unavailable`, маскируя поломку контракта. **Рекомендация (contract-first): KB должен опубликовать `docs/openapi.yaml` для kb-search** как источник истины + контрактные тесты у Консьержа.

## 4. platform / rehome.one — заблокирован отсутствием контракта

Консьерж ожидает 1 операцию: `GET /api/v1/users/{user_id}/context` → парсит `display_name`, `premises[]{id,address,kind}`, `bookings[]{id,status,start_date,end_date}` (денежные поля сознательно не читаются — whitelist, G1). Изоляция сделана правильно (Protocol + единая точка маппинга, graceful degradation).

| # | Серьёзность | Расхождение | Фикс |
|---|---|---|---|
| R-1 | **BLOCKER** | **Контракта rehome.one не существует** нигде; ADR-0006 (на который ссылается ТЗ §9) в репо Консьержа даже не заведён; адаптер написан «вслепую» | получить openapi/контракт от владельца rehome.one |
| R-2 | **BLOCKER** | Композитный `/users/{id}/context` придуман Консьержем; провизорный контракт kb-support (ADR-0006) — per-entity (`/users/{id}`, `/premises/{id}`, `/bookings/{id}`). Минимум один не совпадёт с боем | привести к фактической форме после фиксации |
| R-3 | **BLOCKER** | Имена дат: Консьерж `start_date/end_date`; kb-support `period_start/period_end` → тихая потеря сроков брони | согласовать после контракта |
| R-4..6 | MINOR | типы id не валидируются; семантика `X-On-Behalf-Of` не подтверждена (CC-1, риск G2/G7); деградация маскирует несовместимость | после контракта |

**Вывод:** **заблокирован внешней зависимостью** (TD-PA-001, P1 у kb-support). Это не код-долг Консьержа. До включения нужен подтверждённый контракт rehome.one, затем — завести ADR-0006 в репо Консьержа + синхронизировать форму с kb-support, чтобы оба модуля били в один боевой контракт.
